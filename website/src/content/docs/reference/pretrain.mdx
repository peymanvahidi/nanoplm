`nanoplm pretrain get-yaml` writes a 207-line `pretrain.yaml` with three blocks: `model:` (architecture), `pretraining:` (the training loop), and `resume:` (restarting from a checkpoint). The tables below are extracted from that template and the config dataclasses behind it, so they cannot drift from the tool. Launch with `nanoplm pretrain from-yaml --pure-torch`.

## Where to start

A normal run touches roughly a dozen keys. The rest have defaults that work.

- **Point at the data**: [`dataset_dir`](#pretrain-pretraining-dataset_dir) and [`ckp_dir`](#pretrain-pretraining-ckp_dir). Sequence length is **not** here — it comes from the dataset's `.data_manifest`.
- **Size the model**: [`hidden_size`](#pretrain-model-hidden_size), [`intermediate_size`](#pretrain-model-intermediate_size), [`num_hidden_layers`](#pretrain-model-num_hidden_layers), [`num_attention_heads`](#pretrain-model-num_attention_heads).
- **Size the batch**: [`micro_batch_seqs`](#pretrain-pretraining-micro_batch_seqs) is **sequences** per GPU per forward pass (the VRAM knob); [`global_batch_tokens`](#pretrain-pretraining-global_batch_tokens) is **tokens** per optimizer step. Gradient accumulation is inferred from those two plus the manifest's sequence length and your world size — you never set it.
- **Set the duration**: a **token budget**, not epochs. With the default [`lr_schedule`](#pretrain-pretraining-lr_schedule) of `wsd`, the budget is [`stable_tokens`](#pretrain-pretraining-stable_tokens) plus [`decay_tokens`](#pretrain-pretraining-decay_tokens). With `warmup_stable`, `cosine`, or `linear` it is a single [`train_tokens`](#pretrain-pretraining-train_tokens) budget instead.
- **Pick an optimizer**: [`optimizer`](#pretrain-pretraining-optimizer) and its learning rate — [`adam_learning_rate`](#pretrain-pretraining-adam_learning_rate), or [`muon_learning_rate`](#pretrain-pretraining-muon_learning_rate) for the Muon family. See [Choose an optimizer](/nanoplm/guides/optimizers/).

Two semantics catch people out. **`stable_tokens` includes warmup** — it is the point at which decay begins, not a length added after warmup. `decay_tokens` *is* a length, added on top of it. See [Cooldown and resuming](/nanoplm/guides/cooldown-and-resume/).

Every token budget has a step-based twin — [`stable_steps`](#pretrain-pretraining-stable_steps), [`decay_steps`](#pretrain-pretraining-decay_steps), [`max_steps`](#pretrain-pretraining-max_steps) — that replaces it. Set exactly one of each pair, never both. The template ships these (and `train_tokens`) commented out, because a template that set both forms at once would fail to load; they are documented in the tables below, behind the advanced toggle.

:::caution[Two traps that bite on the first run]
The stock `resume:` block ships `mode: "decay"` with the decay fields filled in, so flipping only [`is_resume`](#pretrain-resume-is_resume) to `true` gives you a **decay** run rather than a continuation — set [`mode`](#pretrain-resume-mode) explicitly. Separately, `optimizer: muonh` fails at startup out of the box, because [`wo_init`](#pretrain-model-wo_init) defaults to `zero` and MuonH forbids that; set `wo_init: kaiming`.
:::

## Reading the tables

Each table hides its **advanced** rows behind a *Show advanced fields* checkbox above it. Tick it to reveal them. Advanced covers four kinds of field:

- The experimental architecture features and their tuning knobs — Canon layers, RePO, mHC-lite, differential attention, paired-head attention, NOBLE, MoE, recycling.
- The FP8, `torch.compile`, and layerwise-debug knobs.
- The step-based duration overrides (`train_tokens`, `stable_steps`, `decay_steps`, `max_steps`).

Most of them are pure-torch only, but not all — a few FP8 rows are Transformer Engine recipe knobs. The **Backend** column is the authoritative per-field answer, so read it rather than the toggle label. Pure-TE supports a strictly smaller surface than pure-torch; see [Choose a backend](/nanoplm/guides/backends/) and the [compatibility matrix](/nanoplm/reference/compatibility/).

## resume

The `resume:` block's template comment calls `lr_decay_to_fraction` an optional override for `mode: decay`. That comment is wrong: decay mode **requires** it, and the run raises `resume decay requires lr_decay_to_fraction` without it. `decay_shape` genuinely is optional and falls back to `1-sqrt`.

Backend selection lives outside all three blocks, as the top-level `pure_torch:` / `pure_te:` booleans shown commented out at the bottom of the template. Prefer the `--pure-torch` / `--pure-te` CLI flags, which override them. When a config fails to load, [Troubleshooting](/nanoplm/troubleshooting/) lists every validation error with its fix.
