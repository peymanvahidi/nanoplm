## What each file owns

Each YAML answers exactly one question. Where a stage needs a fact that another stage already decided, it reads it from an artifact rather than asking you to type it twice.

| File | Owns | Deliberately does not own |
| --- | --- | --- |
| `data.yaml` | **What data.** Which FASTA, how it is filtered, how long a sequence may be, how it is sharded. | Anything about the model. |
| `pretrain.yaml` | **What model, and how long.** Architecture, optimizer, LR schedule, token budget. | Sequence length and register tokens: the data stage already fixed those. |
| `eval.yaml` | **Which checkpoint, which benchmarks.** | The model architecture: the checkpoint carries it. |

## The artifact contract

The three stages are decoupled through two artifacts on disk. This is the whole design, and it is why the configs stay small.

### `data` writes shards plus a manifest

`nanoplm data from-yaml` tokenizes your FASTA into binary shards and writes a `.data_manifest` next to them:

<FileTree>

- output/data/pretrain_data/
  - train/
    - shard_0000.bin
    - shard_0000.idx.npy
    - …
  - val/
    - …
  - **.data_manifest** the contract

</FileTree>

The manifest is a small YAML file recording every decision the data stage made that a later stage needs to know about. It is written for you and marked `DO NOT EDIT`: regenerate it by re-running `nanoplm data from-yaml`, never by hand, because editing it makes it disagree with the shards sitting next to it.

```yaml title=".data_manifest"
pipeline_mode: pretrain     # which pipeline these shards were built for
seqs_num: 20000
min_seq_len: 20
max_seq_len: 512            # <- the number pretraining does its token math with
val_ratio: 0.1
train_dir: train            # where the shards live, relative to this file
val_dir: val
train_sequences: 18000
val_sequences: 2000
num_register_tokens: 0      # <- injected into the model config at pretrain time
sharded: true
samples_per_shard: 5000
total_train_tokens: 4823117 # <- exact token count, used for the epoch estimate
created_at: '2026-07-19T14:07:19'
```

Every field is there because some later stage would otherwise have to ask you for it, or guess:

- **`pipeline_mode`** is the safety check. Pretraining refuses shards built for distillation, and vice versa.
- **`max_seq_len` and `num_register_tokens`** are the tokenization decisions the model must match exactly. They are covered in detail [below](#pretrain-reads-the-manifest-back).
- **`train_dir`, `val_dir`, `sharded`, `samples_per_shard`** are how the loader finds and reads the shards, so no path or layout detail has to be restated in `pretrain.yaml`.
- **`train_sequences` and `val_sequences`** size the dataloader and the evaluation split.
- **`total_train_tokens`** is the exact number of tokens across the training shards, counting BOS, EOS, and register tokens. The data stage is the only place that can know this cheaply (it has just written every shard), so it counts once and records the answer.

That last one is worth spelling out, because it is what turns an abstract token budget into a number you can reason about. In `pretrain.yaml` you set a budget like `train_tokens: 10_000_000`. On its own that says nothing about whether your model will see the dataset twice or two hundred times. Dividing the budget by `total_train_tokens` answers exactly that, and pretraining prints it at startup before it trains anything:

```text title="Output"
Budget: 10,000,000 tokens → ≈2.1 passes over the train set (each sample seen ~2.1×)
```

So a budget of 10M tokens against this 4.8M-token dataset means roughly two epochs. If you expected twenty, you found out in the first second of the run instead of at the end of it. (For a `wsd` schedule the hint is printed once per phase: stable, decay, and total.) Older manifests written before `total_train_tokens` existed still load; pretraining falls back to estimating from the sequence count and length bounds, and tags the line `(approx)` so you know the difference.

### `pretrain` reads the manifest back

This is the fact that explains the whole tool: **`max_seq_len` and `num_register_tokens` are not keys in `pretrain.yaml`.** Pretraining loads them out of `.data_manifest` at startup.

`max_seq_len` is what turns your token budget into optimizer steps. Gradient accumulation is derived from it:

```
grad_accum = ceil( global_batch_tokens / (micro_batch_seqs × max_seq_len × world_size) )
                                                              ^^^^^^^^^^^
                                                        from .data_manifest
```

`num_register_tokens` is copied straight into the model config, so the model's tokenizer matches the tokenizer that wrote the shards. If you could set either of these in `pretrain.yaml`, you could set them *wrong*, and a mismatch between the shards and the model is silent corruption. So the keys do not exist. Set the length once, in [`data.yaml`](/nanoplm/pipeline/data/), and every downstream stage agrees with you.

### `pretrain` writes a self-describing checkpoint

Every checkpoint carries the three configs that produced it:

<FileTree>

- output/pretraining_checkpoints/
  - run-14071932/
    - checkpoint-500/
      - pytorch_model.bin
      - **model_config.yaml** the architecture
      - **pretrain_config.yaml** the training config
      - **data_manifest.yaml** a copy of the data manifest
      - …

</FileTree>

`model_config.yaml` is the full architecture dump: every key the model needs to reconstruct itself. A mid-size MoE run might look like this (most keys omitted):

```yaml title="model_config.yaml"
hidden_size: 1024
intermediate_size: 768
num_hidden_layers: 20
num_attention_heads: 16
num_kv_heads: 8
vocab_size: 32
num_register_tokens: 0      # <- copied from .data_manifest at pretrain time
norm_type: rmsnorm
mlp_activation: srelu
use_qk_norm: true
use_canon_layers: true
# ...
use_moe: true
moe_num_experts: 47
moe_top_k: 3
# ...
```

That is why `eval.yaml` needs nothing but a path. Point `checkpoint_dir` at the directory and the evaluator rebuilds the exact model: no architecture keys to re-type, no chance of loading 12 layers of weights into an 8-layer model.

### A mismatch is caught, not tolerated

The contract is checked, not assumed. Point pretraining at a dataset prepared for a different pipeline and it stops before allocating a single tensor:

```text title="Output"
ValueError: Dataset was prepared for 'distillation' pipeline, but 'pretrain' was expected.
```

The same holds for the config surface itself: every loader rejects keys it does not recognise, so a typo or a stale key from an older release fails loudly at load time instead of quietly training the wrong thing.
