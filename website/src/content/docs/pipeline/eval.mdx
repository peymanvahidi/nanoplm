Evaluation answers the only question that matters: did the model learn anything useful?

This is where the checkpoint format pays off. `eval.yaml` needs **a path and a list of benchmarks**, nothing else. The architecture, the tokenizer, the register-token count, and the training step are all read out of the checkpoint's own `model_config.yaml`, `pretrain_config.yaml`, and `data_manifest.yaml`. There is no architecture to re-declare, so there is no architecture to get wrong.

## Before you start

Benchmarking runs on [biotrainer](https://github.com/sacdallago/biotrainer) 2.1.1, which is an optional
dependency (not part of `nanoplm deps install`; see [Install](/nanoplm/start/install/)):

```sh
uv pip install "nanoplm[eval] @ git+https://github.com/peymanvahidi/nanoplm"
# or, for an editable checkout:
uv pip install -e ".[eval]"
```

Evaluation loads **pure-torch checkpoints only**. That is one more reason to keep the stock `pure_torch: true` default when you pretrain, as [2. Pretrain](/nanoplm/pipeline/pretrain/) recommends.

:::note[Zero-shot only]
`nanoplm eval` covers biotrainer's **zero-shot** frameworks. The supervised probe
benchmarks (`pbc`, `flip`) were dropped in the move to biotrainer 2.0.0; a config
that still lists them fails with a message naming the replacement.
:::

## The whole config

`eval.yaml` is short enough to show in full.

```yaml title="eval.yaml"
eval:
  # A checkpoint-* directory, or a run-* directory (the newest checkpoint inside it is used).
  checkpoint_dir: "output/pretraining_checkpoints/run-14071932/checkpoint-final"

  framework: [pgym]                   # one or more of: pgym, pbc_zeroshot_contact

  output_dir: "autoeval_output"

  # device: cuda                      # auto-detected when omitted
  # embedder_name: my-run             # defaults to the checkpoint directory's name

  zero_shot_method: masked_marginals  # masked_marginals | wt_marginals | pseudoperplexity

  zero_shot_batch_size: 60            # sequences per forward pass: the VRAM knob here

  development_mode: true              # subsampled tasks; false for final numbers

  # dataset_dir: "/path/to/data"      # pre-downloaded benchmarks, for offline machines

  force_download: false               # re-download benchmark datasets
```

## Pointing at a checkpoint

[`checkpoint_dir`](/nanoplm/reference/eval/#eval-checkpoint_dir) accepts either shape:

- A **`checkpoint-*` directory**: that exact checkpoint is evaluated.
- A **`run-*` directory**: the checkpoint with the highest step inside it is evaluated.

So during a long run you can leave `checkpoint_dir` pointed at the run directory and re-run evaluation whenever you want the latest score, without editing the config. The resolved path is echoed on the first line of the output, so you always know which checkpoint produced a number.

## Choosing benchmarks

[`framework`](/nanoplm/reference/eval/#eval-framework) is a list; you can run several in one invocation.

| Value | What it measures |
| --- | --- |
| `pgym` | ProteinGym, **zero-shot**: the model scores mutants directly, with no probe trained on top. |
| `pbc_zeroshot_contact` | Contact maps derived from the model's **categorical Jacobian**, scored against experimental structures. |

Both use the MLM head itself rather than a trained probe, so they measure how well the model models proteins — `pgym` through mutational effects, `pbc_zeroshot_contact` through the pairwise couplings the model has internalised.

Zero-shot scoring has three methods, set by [`zero_shot_method`](/nanoplm/reference/eval/#eval-zero_shot_method) and used only when `pgym` is in `framework`:

- `masked_marginals` (default): mask each mutated position and read the log-probabilities. Slowest and usually the strongest.
- `wt_marginals`: a single forward pass over the wild-type sequence.
- `pseudoperplexity`: the full pseudo-log-likelihood of the mutant.

`pbc_zeroshot_contact` ignores `zero_shot_method`; it always uses the categorical Jacobian.

## Batch size

[`zero_shot_batch_size`](/nanoplm/reference/eval/#eval-zero_shot_batch_size) is the one VRAM knob. biotrainer scores masked-marginals **one masked position per forward pass**; nanoPLM batches positions that share a scoring window into a single forward instead, which is where nearly all the wall-clock goes. The same setting sizes the Jacobian batches for `pbc_zeroshot_contact`.

Positions are grouped by window length so every row in a batch has identical length — no padding is introduced, and each row sees exactly the token slice the per-position path would have passed. A token budget caps the batch for very long windows, so raising this value cannot silently blow up memory on long sequences.

:::caution[Mixture-of-experts checkpoints]
An MoE forward pass is not batch-composition invariant: what else shares the batch can shift a sequence's logits slightly. Scores for MoE checkpoints will therefore differ marginally from an unbatched run. Set `zero_shot_batch_size: 1` if you need to reproduce older unbatched numbers exactly.
:::

## Development mode

[`development_mode`](/nanoplm/reference/eval/#eval-development_mode) defaults to `true`, which evaluates a subsampled slice of each benchmark. That is the right setting while iterating. Set it to `false` for numbers you intend to report.

## Offline machines

Benchmark datasets are downloaded on first use into `~/.cache/biotrainer/autoeval/`. On a cluster whose compute nodes have no outbound network, download once somewhere with internet and point [`dataset_dir`](/nanoplm/reference/eval/#eval-dataset_dir) at the resulting tree. `dataset_dir` and `force_download` are mutually exclusive: a pre-populated directory does not use the download cache that `force_download` clears.

biotrainer 2.1 changed the dataset layout. If `~/.cache/biotrainer/autoeval` still holds datasets from an older biotrainer, `nanoplm eval` refuses to start without `dataset_dir`, because 2.1 would reuse the old files instead of downloading the current ones. Point `dataset_dir` at a fresh directory, or delete the cache.

`force_download` deletes the whole `~/.cache/biotrainer/autoeval` directory before downloading, including datasets another biotrainer install may still use. To get a fresh copy without touching that cache, set `dataset_dir` to an empty directory instead.

## What you get

<FileTree>

- autoeval_output/
  - autoeval_report_checkpoint-final.json the combined report
  - checkpoint-final/ the embedder name: defaults to the checkpoint directory's name
    - PGYM/
      - … per-task outputs and the zero-shot result cache
    - PBC_ZEROSHOT_CONTACT/
      - …

</FileTree>

A second framework added to `framework:` later merges into the same report rather than starting a new one. That also means a framework already present in the report is **reused, not recomputed** — the run logs a warning naming which ones were served from disk. Delete the report, or use a fresh `output_dir`, to force a re-run.
