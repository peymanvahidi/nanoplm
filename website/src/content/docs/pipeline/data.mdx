This step turns a FASTA file into what pretraining reads: tokenized sequences in binary shard files under `train/` and `val/`, and a small `.data_manifest` file that records how they were built. You edit one file, `data.yaml`, and run one command.

## Run it

<Steps>

1. Scaffold the config.

   ```sh
   nanoplm data get-yaml
   ```

   ```text title="Output"
   Wrote data.yaml and dvc.yaml in <cwd>.
   Edit data.yaml and run `nanoplm data from-yaml` to execute.
   ```

2. Edit `data.yaml` (the whole file is shown [below](#the-whole-config)). The template already builds 20,000 SwissProt sequences, so you can run it as it is.

3. Run the pipeline.

   ```sh
   nanoplm data from-yaml
   ```

   ```text title="Output (trimmed)"
   data.yaml: 1 source -> <cwd>/output/data/pretrain_data
   source     fasta                         max seqs  len     val  cluster subsampling
   swissprot  uniprot_sprot.fasta.gz (url)  20,000    20-512  0.1  off
   Regenerated <cwd>/dvc.yaml
   Initialized DVC repository in: <cwd> (cache.type hardlink,symlink)
   Rebuild: all (first run)
   Running dvc repro (full pipeline)...
   # ...
   Wrote manifest: output/data/pretrain_data/.data_manifest

   Pretraining data pipeline complete.

     Source:          https://ftp.uniprot.org/pub/databases/uniprot/knowledgebase/complete/uniprot_sprot.fasta.gz
     Total sequences: 20000
       Train:         18000
       Val:           2000
     Manifest:        <cwd>/output/data/pretrain_data/.data_manifest
     Set pretrain.yaml's dataset_dir to <cwd>/output/data/pretrain_data.
   ```

</Steps>

`from-yaml` runs these stages in order, through [DVC](https://dvc.org/):

```
download → extract → check → shuffle → filter → split → tokenize → write manifest
```

`from-yaml` rewrites `dvc.yaml` from your `data.yaml` each time, so never edit `dvc.yaml`. DVC remembers what each finished stage produced. A second run, or a run after an interrupted one, skips every stage whose inputs have not changed. A download cut off halfway starts again from the beginning.

## Use your own FASTA

Point `fasta` at the file. A relative path starts from the folder `data.yaml` is in. nanoPLM reads the file where it is and never copies it. You pick the source name (`mine` here). It is also the name of the folder that holds this source's intermediate files.

```yaml title="data.yaml"
sources:
  mine:
    fasta: my_proteins.fasta   # or .fa, and either one as .gz or .zst
```

`fasta` accepts three kinds of value:

- a shortcut for a UniProt file, from the table below;
- a URL (`http://`, `https://` or `ftp://`), downloaded once into `output_dir/downloads/`;
- a local `.fasta` or `.fa` file, optionally compressed as `.gz` or `.zst`.

| Shortcut | URL |
| --- | --- |
| `swissprot` | `https://ftp.uniprot.org/pub/databases/uniprot/knowledgebase/complete/uniprot_sprot.fasta.gz` |
| `trembl` | `https://ftp.uniprot.org/pub/databases/uniprot/knowledgebase/complete/uniprot_trembl.fasta.gz` |
| `uniref50` | `https://ftp.uniprot.org/pub/databases/uniprot/uniref/uniref50/uniref50.fasta.gz` |
| `uniref90` | `https://ftp.uniprot.org/pub/databases/uniprot/uniref/uniref90/uniref90.fasta.gz` |
| `uniref100` | `https://ftp.uniprot.org/pub/databases/uniprot/uniref/uniref100/uniref100.fasta.gz` |

A `*` at the end of a sequence is a stop codon (Prodigal writes one). The `filter` stage removes it before the length filter. A `*` anywhere else makes the sequence [invalid](#invalid-sequences-will-stop-you-once).

Start with SwissProt (about 570k sequences). It downloads in minutes, so you can test the pipeline on it before a UniRef-scale run.

To reuse a dataset another `data.yaml` already built, write `prepared: <its output_dir>` instead of `fasta`. `from-yaml` checks that folder's manifest, prints what it holds and builds nothing. With only a `prepared` source, you can leave out `output_dir`.

To train on one random member of every cluster per epoch (for example UniRef90 sequences under UniRef50 clusters), set `cluster_subsampling: true` on the source, or a block with `members` or `clusters`. See [Cluster subsampling](/nanoplm/guides/cluster-subsampling/).

## The whole config

This is the template with its commented examples left out.

```yaml title="data.yaml"
output_dir: "output/data/pretrain_data"   # every file goes here; pretrain.yaml's dataset_dir points here

# One entry per FASTA. Several entries make a mix.
# weight = share of training sequences (not tokens); weights must sum to 1.
sources:
  swissprot:
    fasta: swissprot     # swissprot, trembl, uniref50, uniref90, uniref100, a URL, or a local .fasta/.fa (.gz/.zst)
    weight: 1.0          # 0.2 when mixed with uniref50 below
    # max_seq_len: 1024  # a data_params field set here overrides it (not val_ratio / val_size)

  # (a commented UniRef50 cluster-subsampling source with weight 0.8 and a
  #  commented another_source follow)

data_params:
  max_seqs: 20000        # -1 = all
  min_seq_len: 20        # shorter sequences are dropped
  max_seq_len: 512       # longer sequences are dropped
  val_ratio: 0.1         # share of the mix held out for validation
  # val_size: 150000     # or a fixed number of val sequences; set only one of the two
  drop_invalid_sequences: false  # true: drop sequences with unknown residues instead of stopping

  # Rarely changed
  shuffle: true          # shuffle before the train / val split
  shuffle_seed: 24
  samples_per_shard: 2000  # sequences per shard file; raised automatically for large cluster datasets
  max_workers: 2         # tokenizer processes and MMseqs2 threads; -1 = all cores
  register_tokens: 0     # 0, 1 or 2 scratch tokens after EOS
```

With one source, `weight` must be `1.0` or left out. Two or more sources make a mix, drawn by `weight`: see [Mixing datasets](/nanoplm/guides/mixing/).

`max_seqs`, `min_seq_len`, `max_seq_len` and one of `val_ratio` or `val_size` are required. `val_ratio` is the share of the sequences held out for validation; `val_size` is a number of them. Set either one only in `data_params`, not on a source. In a mix it sets the validation sequences of the whole mix: see [Mixing datasets](/nanoplm/guides/mixing/#validation). You can leave out the other `data_params`. The template's values are the defaults, so deleting one, or writing it out, reruns nothing. The [data.yaml reference](/nanoplm/reference/data/) describes each key.

:::caution[max_seq_len is set here and nowhere else]
`from-yaml` writes `max_seq_len` into `.data_manifest`. Pretraining reads it from there to compute gradient accumulation, `grad_accum = ceil(global_batch_tokens / (micro_batch_seqs × max_seq_len × world_size))`, so `pretrain.yaml` has no `max_seq_len` key. To train on longer sequences, change it here and run `from-yaml` again. The shards change too.
:::

Attention cost grows with the square of the sequence length, so `512` is a cheap place to start. Raise it when your proteins need the context.

## Read the table before the run

Before any stage runs, `from-yaml` prints one row per source and one line saying what will run. Check it. A wrong `fasta`, a forgotten `max_seqs` or an unexpected full rebuild shows up here, before hours of work.

```text
data.yaml: 1 source -> /work/output/data/pretrain_data
source  fasta                               max seqs  len     val  cluster subsampling
mine    my_proteins.fasta (local, 66.0 kB)  200       20-512  0.1  off
Regenerated /work/dvc.yaml
Rebuild: all (first run)
```

| Column | Shows |
| --- | --- |
| `fasta` | The file the stages read, and where it comes from. `(url)` means it will be downloaded. `(reuse, 40.2 kB, 2026-09-01)` means a file with that name, written on that date, is already in `output_dir/downloads/`. `(local, 66.0 kB)` means a local file. |
| `max seqs` | `max_seqs`, or `all` for `-1`. A cluster source counts clusters: `all clusters`, `20,000 clusters`. |
| `len` | `min_seq_len`-`max_seq_len`. |
| `val` | `val_ratio`. In a mix, or with `val_size`, `by weight`, and a line under the table gives the size of the whole mix's validation split. |
| `cluster subsampling` | `off`, or where the clusters come from and what the source trains on. See [Cluster subsampling](/nanoplm/guides/cluster-subsampling/#read-the-table). |

A `*` after a value means the source sets it itself instead of taking it from `data_params`.

The line under the table is one of:

| Line | Meaning |
| --- | --- |
| `Rebuild: all (first run)` | Nothing has been built in this folder yet. |
| `Up to date: all stages` | Nothing changed since the last run. DVC skips every stage. |
| `May rerun (DVC skips a stage its run cache already has): filter, split, ... Up to date: check, shuffle.` | Your edit changed the inputs of the listed stages, so they run again. If DVC has already run a stage with exactly these inputs, for example because you changed a value and then changed it back, it restores that output instead. |

`reuse` only means the file exists. DVC reuses a download that an earlier `from-yaml` run in this folder wrote. It does not know about a file you copied into `downloads/` yourself, so it deletes that file and downloads again. To use a FASTA you already have, set `fasta` to its path.

To see the table and the stages that would run without running them, use `nanoplm data from-yaml --dry-run`. Two limits apply:

- `from-yaml` must have run once in this folder first, because `--dry-run` does not set up DVC.
- The preview stops at the first download that has not happened yet. DVC cannot plan the stages that read a file that does not exist.

## Invalid sequences will stop you once

Real FASTA files contain residues outside the 20 standard amino acids. The `check` stage finds them. With the default `drop_invalid_sequences: false` it stops the pipeline, so your dataset never changes without you knowing:

```text title="Output (trimmed)"
Running stage 'check':
> nanoplm data check -i my_proteins.fasta -o output/data/pretrain_data/mine/validation --drop-invalid false
WARNING check: found 2 invalid sequence(s); see output/data/pretrain_data/mine/validation/invalid.fasta
Error: Validation found 2 problematic sequence(s).
  Inspect: output/data/pretrain_data/mine/validation/invalid.fasta
  Summary: output/data/pretrain_data/mine/validation/validation.json

To exclude these sequences and continue the pipeline:
    nanoplm data from-yaml --fix
```

Look at `invalid.fasta` first. A large count usually means the file is not what you thought it was. To drop those sequences and continue:

```sh
nanoplm data from-yaml --fix
```

```text title="Output (first line)"
Set data.yaml: drop_invalid_sequences=true
```

`--fix` sets `drop_invalid_sequences: true` in your `data.yaml`, everywhere it appears, and runs again. The `filter` stage then drops the IDs listed in `<source>/validation/invalid_ids.txt`. The change is in your file, so `git diff` shows it.

## What you get

<FileTree>

- output/data/pretrain_data/ point pretraining.dataset_dir here
  - downloads/
    - uniprot_sprot.fasta.gz downloaded, one file per URL
  - swissprot/ this source's intermediate files
    - uniprot_sprot.fasta extracted
    - validation/
      - validation.json
      - invalid.fasta
      - invalid_ids.txt read by the filter stage
    - shuffled.fasta
    - filtered.fasta
    - split/
      - train.fasta
      - val.fasta
  - train/
    - shard_0000.bin uint8 token ids
    - shard_0000.idx.npy per-sequence lengths
    - …
  - val/
    - …
  - .data_manifest

</FileTree>

The manifest describes the shards. Pretraining reads it:

```yaml title="output/data/pretrain_data/.data_manifest"
# This file is AUTO-GENERATED by 'nanoplm data from-yaml'.
# DO NOT EDIT THIS FILE MANUALLY.
# To regenerate, run 'nanoplm data from-yaml' again with updated params.yaml.

pipeline_mode: pretrain
seqs_num: 20000
min_seq_len: 20
max_seq_len: 512
val_ratio: 0.1
train_dir: train
val_dir: val
train_sequences: 18000
val_sequences: 2000
num_register_tokens: 0
created_at: '2026-07-14T19:32:04.118273'
sharded: true
samples_per_shard: 2000
total_train_tokens: 6392418
```

Never edit this file. To change a value in it, change `data.yaml` and run `from-yaml` again.

## Disk use and the DVC cache

DVC keeps a cache of every output in `.dvc/cache`, next to `data.yaml`. When `from-yaml` sets up DVC in a new folder, it sets `cache.type hardlink,symlink`, so the cache links to your outputs instead of holding a second copy.

- Linked outputs are read-only. Run `dvc unprotect <path>` before you edit one.
- If `output_dir` and `.dvc/cache` are on different file systems, DVC uses symlinks and the data itself lives in `.dvc/cache`. Deleting the cache then breaks the dataset.
- After you change settings, `dvc gc --workspace` deletes the cached versions that the current outputs no longer use.
- A folder where DVC was set up earlier, by an older nanoPLM or by your own `dvc init`, keeps its own `cache.type`. That is often a copy cache, which stores every output twice. To switch it to links, run `dvc config cache.type hardlink,symlink` and then `dvc checkout --relink` in the folder of `data.yaml`.

## Move an old data.yaml

A `data.yaml` from before the `sources:` layout has a `data_dirs` block with `url` or `local_fasta` and seven paths. It still works. `from-yaml` reads it as one source named `main`, builds the same files in the same places, and prints the new layout to paste in:

```text title="Output"
Warning: data_dirs is the old data.yaml layout. It still works, read as one source named "main". To switch, replace data_dirs with:

output_dir: "output/data/pretrain_data"
sources:
  main:
    fasta: swissprot

and rename data_params.seqs_num to max_seqs. The new layout keeps intermediate files under output_dir/main/, so the first run after switching rebuilds them.
To skip the download, set fasta: "output/data/raw/sequences.fasta.gz" (the file already downloaded; it is read where it is, so keep it).
Then these old files can be deleted: output/data/raw/sequences.fasta, output/data/validation, output/data/raw/sequences_shuffled.fasta, output/data/filter/sequences_filtered.fasta, output/data/split.
```

To switch:

1. Delete the `data_dirs` block and paste the printed `output_dir` and `sources` in its place. A file with both layouts is an error.
2. Rename `seqs_num` to `max_seqs` under `data_params`. The old name still works, with a warning.
3. Run `from-yaml`. The first run rebuilds the intermediate files under `output_dir/main/`, then the shards.

If the folder's DVC cache stores every output twice, see [Disk use and the DVC cache](#disk-use-and-the-dvc-cache).
